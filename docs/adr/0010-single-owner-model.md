# ADR-0010：单一所有者模型与个人版密钥保管

- 状态：已接受
- 日期：2026-09-27（同日按 v0.2.1 一致性裁决修订：密钥保管、跨站点共享、访问记录归档）；2026-09-28 勘误：Phase 1 的密钥保管与审计（依据 [Phase 1 实现规格](../impl/phase1-spec.md) D-06、I-27，见文末"勘误"）
- 相关：[01 整体架构](../01-architecture.md)、[05 AI Agent 策略](../05-ai-agent-policy.md)、[06 策略引擎、后台与审计](../06-policy-console-observability.md)、[10 威胁模型](../10-threat-model.md)、[ADR-0009](0009-ja4-only-licensing.md)

## 背景

- 平台只由所有者本人使用，只保护其自有的几个网站。
- 原设计面向多租户：Tenant 层级、按租户隔离数据与密钥、跨租户情报共享、多角色 RBAC 与 SSO、生产发布的两人审批。
- 单人无法满足"提交人与审批人不能是同一人"；为不存在的租户维护隔离、为几把密钥部署专门的密钥服务，只增加复杂度与成本。
- 平台自用，但受保护网站的访客数据仍受 PIPL 等法规约束；网站作为网络运营者有日志留存要求。

## 决策

1. **层级**：Site → Environment → Route → Policy Set，去掉 Tenant 层。数据按 site 隔离（Valkey key 前缀、事件中的 site 字段）；IP / ASN 类实体 verdict 可在所有者各站点间共享，按站点开关（[01 §10](../01-architecture.md#10-站点模型)）。
2. **删除**：多租户、SaaS、计费、跨租户情报共享、多角色 RBAC 与 SSO。
3. **登录**：所有者本人，passkey（WebAuthn）为主、TOTP 备用；可选一个只读账号。
4. **替代两人审批**：敏感操作需要重新认证 + 明确确认（输入站点名）+ 可选生效延迟，全部写审计；下表为主要类别，完整清单与默认值见 [06 §4](../06-policy-console-observability.md#4-管理后台)。

| 敏感操作 | 说明 |
|---|---|
| 生产策略发布 | 发布到生产环境的策略包 |
| 带 `scan` 能力的测试授权工单 | 单人流程，见 [05 §5](../05-ai-agent-policy.md#5-测试授权工单) |
| 密钥轮换 | 凭证、Challenge 密封、配置签名、Provider secret |
| 删除审计以外的数据 | 审计本身不可删除 |

5. **密钥保管**：默认用本机加密的密钥文件——Edge / 控制面主机以 systemd credentials（`systemd-creds`，有 TPM2 时绑定）交付；工作站上的配置签名私钥用 age 加密（口令或硬件密钥插件）；云 KMS 可选；不部署 OpenBao。配置签名密钥为所有者**一对**（Ed25519，`kid` 轮换，年更），Phase 1 由 mgctl 在工作站签名，Phase 3 起移到大脑 VM 的 mg-control；凭证密钥、Challenge 密封密钥、Turnstile secret 按站点。轮换周期见 [06 §8](../06-policy-console-observability.md#8-平台自身安全)。
6. **审计与合规**：保留哈希链，每日锚点签名后写入对象存储（云厂商支持时开启对象锁）。平台不需要作为服务通过等保测评；访客数据仍按 PIPL 等处理；最小访问记录（假名化、不采样）每日归档对象存储 ≥ 6 个月（[02 §9](../02-data-flow.md#9-采样与保留)）。
7. **工期与范围**：按单人开发估算（见 07）；不向他人提供，包括托管服务（ADR-0009）。

## 备选方案

| 方案 | 不采用的原因 |
|---|---|
| 保留多租户以备将来 | 复杂度与成本长期存在；对外提供还会改变 JA4+ 许可与合规范围 |
| 同一人两个账号走两人审批 | 形式上的职责分离，不增加安全性 |
| 邀请第二人审批 | 自用场景不现实，且让他人接触访客数据 |
| OpenBao 或云 KMS 作为默认密钥库 | 多一个有状态组件或云依赖；几个站点的密钥用本机加密文件即可，云 KMS 保留为可选 |

## 后果

- 数据模型、配置包与后台明显简化；站点级密钥按站点管理，配置签名密钥只有一对。
- 单账号被攻破的影响面更大：以 passkey、重新认证、生效延迟与审计锚点降低风险；配置签名私钥不在 Edge 上，签名主机（工作站 / 大脑 VM）失陷时按 `kid` 轮换。
- 若将来要保护他人站点，需要新 ADR：重新引入租户隔离，并复核许可（ADR-0009）与合规范围。
- 05 的测试授权工单与 06 的角色、发布流程按本 ADR 调整为单人流程。

## 勘误（2026-09-28，Phase 1 实现）

结论不变。Phase 1 的实际做法（细节见规格 [§12.6–§12.8](../impl/phase1-spec.md#126-所有者签名密钥)、[§17](../impl/phase1-spec.md#17-所有者运维手册代码之外)）：

| 项 | Phase 1 |
|---|---|
| 工作站上的密钥（决策 5） | 不只配置签名私钥：站点凭证密钥、封装根密钥、假名化密钥与上游密钥头值都以 age（scrypt 口令，工作因子缺省 18）加密文件保存，工作站上不留明文；`mgctl keys export` 把明文经管道直接交给 Edge 主机上的 `systemd-creds encrypt`，systemd 单元用 `LoadCredentialEncrypted=` 交付 |
| 新增密钥 | 所有者级假名化密钥 `K_pseudo`：Valkey 键与 `mg:ev` 中标识个人的部分用它做 HMAC，跨站共享的 verdict 键因此与站点无关（D-06）；上游密钥头值（1–2 个，[ADR-0004](0004-origin-protection-tunnel-aop.md)） |
| 配置签名密钥 | `kid` 由所有者命名（如 `owner-2026`，只允许小写字母、数字与 `._-`）；Edge 的 `[trust] owner_keys` 可同时列两把公钥，轮换顺序为"先加新公钥 → 用新密钥发布 → 所有 Edge 生效后删旧公钥" |
| 审计（决策 6） | Phase 1 为 mgctl 的本地 JSON Lines 哈希链（`mgctl audit verify` 校验）；写命令在任何写入或出站请求之前先确认日志可追加，否则不执行并返回 3（I-27）；每日锚点签名与对象存储随 mg-control 在 Phase 3 |
| 生效延迟（决策 4） | 站点 YAML 的 `not_before` 提供可选的延迟生效；Phase 1 的"重新认证 + 确认"对应 mgctl 的口令与 `bundle publish --confirm <site>` |
